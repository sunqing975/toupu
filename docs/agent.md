# agent.md — 开发约束与防漂移规范

> 本文件是本仓库开发 Agent（包括 IDE 编码 Agent、CLI Agent、ChatGPT 等）的最高优先级项目约束。开始任何代码修改前必须阅读本文件及 `docs/` 下相关文档。遇到需求与本文档冲突时，先指出冲突并提出修订建议，不得自行改变核心架构。

## 1. 项目定位

开发的产品是**投谱（Toupu）**：一个**个人投资资产管理与决策系统**，第一版仅支持中国市场：

- 场外公募基金
- 场内 ETF
- A 股股票
- 现金及银行/证券/基金平台账户

数据录入方式为手动录入 + Excel/CSV 导入。系统提供完整投资账本、持仓核算、收益分析、风险提醒和 Agent 接口。第一版不自动下单、不连接券商执行交易。

## 2. 不可违反的架构原则

1. **Ledger is the source of truth.** 交易、成交、资金/资产分录是事实；持仓、余额、收益、图表和快照是可重建的派生结果。
2. **业务事件与账务分录分离。** `investment_transactions` 描述业务发生了什么；`journal_entries/journal_lines` 描述资产如何变化。
3. **场外基金与场内证券分开处理。** 共用标的、账户、账本基础设施，但使用不同的业务处理器和验证规则。不得用一套股票成交逻辑处理基金申赎。
4. **证券成交以 execution 为准。** 股票/ETF 的持仓变化来自实际成交明细，不来自委托数量或用户输入的预估金额。
5. **基金份额以确认结果为准。** 场外基金申赎必须保存申请信息和确认净值、确认份额、确认金额、费用；申请提交不等于份额已到账。
6. **已入账数据不可原地修改或删除。** 通过冲正/撤销分录和新交易修正。草稿可以编辑，已确认但未入账的数据按状态规则处理。
7. **金融数值禁止 float。** Python 使用 `Decimal`；数据库使用 `NUMERIC`；JSON/API 对金额和数量优先使用十进制字符串，避免精度丢失。
8. **账务入账原子化。** 交易状态、分录、持仓批次变动必须在同一数据库事务中完成；任何一步失败全部回滚。
9. **借贷必须平衡。** 每个已过账 journal entry 的借方合计必须等于贷方合计；不得以应用层“通常会平衡”代替强制校验。
10. **Agent 不拥有账本写权限。** Agent 默认只读；自然语言交易录入只生成草稿/提案。正式入账必须由用户确认并经过业务服务校验。
11. **风险引擎确定性。** 止盈止损、仓位和回撤阈值由普通代码计算；LLM 不得自行计算后直接触发交易。
12. **数据源可替换。** 业务模块不得直接耦合 AKShare、Tushare、天天基金等供应商 SDK；必须经 Provider/Adapter 接口和标准化层。
13. **模块化单体优先。** 不得无明确需求引入微服务、Kafka、Redis、复杂任务编排或多 Agent。
14. **所有重要操作可审计。** 交易确认、入账、冲正、导入确认、风险规则修改、Agent 提案审批必须留痕。

## 3. 技术约束

- Python 3.12+。
- FastAPI；Pydantic 用于 API 输入输出校验。
- SQLAlchemy 2.x；Alembic 管理所有 schema 变更。
- PostgreSQL 是唯一正式数据库。
- pytest；核心金融计算必须有单元测试和业务场景测试。
- 前端 React + TypeScript；前端不承担权威金融计算。
- Docker Compose 用于本地部署。
- 依赖版本必须锁定；不要随意升级主版本。

## 4. 模块边界

建议按以下领域组织代码：

- `accounts`: 投资账户、账户状态、账户资金属性。
- `instruments`: 基金/ETF/股票标的及代码映射。
- `transactions`: 投资业务事件、状态流转、草稿和确认。
- `executions`: 股票/ETF 实际成交明细。
- `funds`: 场外基金申购赎回申请及确认。
- `ledger`: 科目、分录、过账、冲正、借贷平衡。
- `positions`: 持仓数量、批次、可用数量、成本。
- `performance`: 已实现/未实现盈亏、XIRR、TWR、回撤。
- `corporate_actions`: 分红、送股、转增、拆并股等。
- `market_data`: 行情、净值、交易日历、Provider、数据质量。
- `imports`: 文件上传、模板、字段映射、预览、校验、去重、确认。
- `risk`: 风险规则、确定性计算、风险事件和冷却策略。
- `plans`: 投资计划、Agent 提案和人工审批。
- `notifications`: 邮件/消息/本地通知适配。
- `agent`: REST/MCP 工具、Token scope、审计；不得直接操作 ORM 表。

领域模块之间通过 Service/接口调用，不允许跨模块随意写对方数据库表。

## 5. 交易和账本状态规则

### 交易状态

推荐状态：

- `DRAFT`: 草稿，可修改，不产生账务影响。
- `CONFIRMED`: 用户确认业务信息，等待确认数据/过账。
- `PARTIAL`: 证券委托存在部分成交，持仓只反映已成交部分。
- `POSTED`: 已生成平衡账务分录并更新派生持仓。
- `REVERSED`: 已通过冲正撤销；原记录保留。
- `CANCELLED`: 尚未入账的申请/委托被取消。

不得将 `CONFIRMED` 和 `POSTED` 混为一谈。

### 入账约束

- 一笔已过账业务事件只能对应一组有效的原始 journal entry；冲正记录另行关联。
- 入账必须幂等：相同业务事件重复请求不能重复记账。
- `POSTED` 交易禁止更新核心字段。
- 冲正必须反向生成原分录，并关联原交易/原分录。
- 分录与持仓派生数据在同一事务中更新，或通过可靠的事务内 outbox/重建机制保证一致性。

## 6. 金融计算规范

- 所有金额、份额、价格均使用 `Decimal`。
- 明确每种业务的精度和舍入规则；不允许全局统一 `quantize(0.01)`。
- 原始行情、成交、净值保留数据源精度；展示层才格式化。
- 股票/ETF 成交金额以成交明细为准，费用单独记录。
- 基金确认份额和确认净值以确认数据为准。
- 现金余额、证券数量、成本、已实现损益、未实现损益分开计算。
- 现金分红与红利再投资是不同事件，不得重复计算现金和份额。
- 送股/转增影响数量和单位成本，不应伪造普通买入现金流。
- 不得将未实现市值变动记成真实现金流。
- XIRR/TWR 必须定义外部现金流边界、估值时点、分红处理和缺失行情处理后再实现。
- 不确定的市场规则必须标记为待确认，不得猜测费率、税率、交易单位或交易日规则。

## 7. 数据导入规范

导入文件必须经过：上传 → 原始行保存 → 解析/标准化 → 校验 → 重复检测 → 预览 → 用户确认 → 正式入账。

- 导入阶段不得直接写入正式账本。
- 原始文件哈希用于文件级重复检测；业务级去重还要用外部成交编号或规范化字段组合。
- 原始数据必须保留，便于审计和重新解析。
- 每条错误记录必须返回行号、字段和可读原因。
- 导入确认必须支持幂等。

## 8. Agent 安全边界

- Agent 只能通过明确暴露的 REST/MCP 服务访问系统。
- Agent 不得连接数据库，不得访问数据库凭证。
- 默认只读 scope：账户、持仓、交易、行情、风险、计划查询。
- 写操作先创建 `proposal` 或 `draft`，不得直接入账。
- 用户审批需要明确展示资产、账户、数量、价格/净值、费用、金额和影响。
- 审批后重新校验数据，不可盲目执行过期提案。
- 不提供自动下单工具。
- 工具返回数据应包含数据时间、来源、是否估值/延迟、缺失字段等信息。

## 9. 测试要求

每个业务功能必须包含：

1. 正常路径测试。
2. 边界值测试。
3. 重复请求/幂等测试。
4. 失败回滚测试。
5. 冲正/更正测试（涉及已入账业务时）。
6. 金融数值精度测试。

最低必须覆盖：股票买入卖出、部分成交、基金申购确认、基金赎回、现金入金出金、账户转账、分红、送转股、重复导入、冲正、借贷不平衡拒绝入账。

## 10. 防止需求漂移的工作流程

每次接到开发任务，按以下顺序执行：

1. 先阅读 `agent.md` 和相关领域文档。
2. 用一段话复述任务目标、边界和不做的事情。
3. 找出受影响的领域模块、表、API 和测试。
4. 如果需求改变账务语义，先修改 `docs/ledger-rules.md`，并说明迁移影响；不得直接改代码绕过文档。
5. 先补测试，再实现最小改动。
6. 运行相关测试和静态检查；报告实际执行结果，不得声称未运行的测试通过。
7. 检查是否引入了新的依赖、外部 SaaS、自动交易能力或跨模块耦合。
8. 更新文档和迁移脚本。
9. 最后汇报：改了什么、为什么、测试结果、未解决问题、数据库迁移影响。

## 11. 禁止事项

- 禁止把所有资产塞进一张只有 `code/quantity/price` 的简化表。
- 禁止用 LLM 直接计算正式持仓、成本、收益和风险阈值。
- 禁止用 `float` 处理金额和份额。
- 禁止绕过 PostingService 直接写账务分录或更新持仓。
- 禁止直接修改已入账交易。
- 禁止导入文件未经预览确认就入账。
- 禁止把盘中基金估值当成正式基金净值。
- 禁止将行情源字段直接暴露为核心领域模型字段。
- 禁止未讨论就增加微服务、消息队列、自动交易或多市场实现。
- 禁止为了“代码整洁”重写未涉及且已有测试通过的模块。

## 12. 完成定义（Definition of Done）

一个功能只有在以下条件全部满足时才算完成：

- 业务规则已在文档中定义。
- API 输入输出和错误场景明确。
- 数据库迁移可从空库执行。
- 核心逻辑有自动化测试。
- 金融计算有可人工复核的测试样例。
- 权限、审计、幂等和事务边界已考虑。
- 相关文档已更新。
- 实际测试结果已如实汇报。
